# GenUと源内の違い：プレゼンアウトライン

## 1. GenUと源内の共通点

GenUと源内は、まったく無関係なアプリケーションではない。源内Webは、AWS製OSSのGenU（Generative AI Use Cases）をベースに開発されている。そのため、両者には次の共通点がある。

- AWS上で動作する生成AIを使用したWebアプリケーションである
- チャット、文章生成、要約、翻訳、RAGなどの業務ユースケースを提供する
- ユーザ側でのカスタマイズを想定して作られている。
- かすたまいず/再配布/商用利用が可能なOSSとして公開されている
- 認証を備えた共通のAI利用ポータルとして展開できる

画面構成や技術構成が似ているのは、源内WebがGenUを源流とするためである。一方、現在はそれぞれ独立して開発されており、機能構成と設計目的に違いがある。

## 2. 最初の結論

本番運用、特に官公庁・自治体向けに提供する場合は、源内を推奨する。

GenUは、AWSのさまざまな生成AIサービスを活用したユースケースを迅速に構築し、PoCを行うことを主眼とする。一方、源内は、アクセス管理、組織単位のガバナンス、AIアプリ管理、監視・モニタリングなど、本番運用を見据えて設計されている。

> GenUは「AWSの生成AIサービスを素早く試すPoC向けのアプリケーション」、源内は「行政機関で継続的に本番運用することを見据えたアプリケーション」である。

## 3. 推奨理由：PoCと本番運用の違い

### 3.1 GenUは生成AI機能を迅速に試す

GenUの強みは、AWSの生成AI機能を短期間で導入し、技術的な実現性や業務適合性を検証できることである。

- Amazon KendraまたはKnowledge Bases for Amazon Bedrockを使ったRAG
- Bedrock Agents
- AgentCore Runtimeにデプロイ済みのエージェントの取り込み
- Bedrock Flows
- MCPサーバーとの連携
- 画像生成、動画分析、ユースケースビルダー

個別のAWSサービスに対するWeb画面や認証を一から構築する前に、複数の技術とユースケースを比較・検証できる。したがって、GenUは「何ができるか」「業務に適合するか」を見極めるPoC段階で特に価値が高い。

### 3.2 源内は行政機関での本番運用を考慮する

源内は、行政職員が業務特化のAIアプリを迅速、安全かつ簡単に利用するための基盤である。GenU由来の生成AI機能に加え、組織内で継続的に管理・運用するための機能が追加されている。

| 比較軸 | GenU | 源内 |
| --- | --- | --- |
| 設計の主眼 | AWS生成AIユースケースの迅速な検証 | 行政機関での継続的な本番運用 |
| 主な強み | RAGやAgentCoreなどAWSの多様な機能を試せる | 組織・チーム単位で統制できる |
| 管理 | 汎用的な利用管理 | システム管理者とチーム管理者による階層的な管理 |
| AIアプリ | 多様なAWS生成AI機能の試用 | 外部AIアプリの登録とチーム単位の展開 |
| 運用 | PoCや技術検証の起点 | 監視・モニタリングを含む本番運用を考慮 |
| デザイン | 企業・組織一般向け | デジタル庁デザインシステムとアクセシビリティを考慮 |

## 4. 源内の特徴

### 4.1 チーム単位のアクセス管理

源内のチーム管理は、単なる管理者と一般利用者の権限差ではない。

- システム管理者はすべてのチームとAIアプリを管理する
- チーム管理者は自チームのメンバーとAIアプリを管理する
- 一般メンバーは所属チームのAIアプリを閲覧・実行する
- 共通チームのAIアプリはすべての認証済みユーザーに提供できる

これにより、全庁共通のAIアプリと、部署・業務固有のAIアプリを分けて運用できる。

### 4.2 自治体での利用イメージ

自治体で課・室ごとに利用者を管理する場合、課室を源内のチームに対応させることができる。本庁のシステム管理者が全体を統制しながら、各課室の管理者に自組織のメンバー管理を委任できる。

また、利用ログとユーザー・チーム情報を紐づければ、課室別の利用者数、利用回数、利用するAIアプリなどを可視化する基盤となる。

ただし、次の点は追加設計が必要である。

- アカウントの発行・停止などのライフサイクル管理
- 収集する利用ログと保存期間
- 課室別の集計指標
- 可視化ダッシュボード

公開版の源内Webに、課室別の利用状況ダッシュボードが標準機能として含まれるとは確認できない。ユーザー・チーム管理は、可視化を実現するための組織軸として位置づける。

### 4.3 本番運用のための考慮

源内Webには、監視・モニタリングなどの運用機能が追加されている。また、デジタル庁デザインシステムの適用とアクセシビリティ試験が行われている。

これらは、単にAI機能を試すだけでなく、行政機関の組織と業務の中で継続的に利用することを考慮した特徴である。

## 5. カスタムAIアプリの追加機能

### 5.1 何ができるか

源内Webは、別途開発・デプロイした業務固有のAIアプリを「行政実務用AIアプリ」として登録できる。ここでいう「行政実務用」とは、源内Webの外部に構築し、APIで連携するAIアプリを区別する表現である。

### 5.2 登録から利用までの流れ

1. 業務固有のAIアプリを外部のAI環境に開発・デプロイする
2. 源内WebのAPI仕様に従うREST APIを用意する
3. 管理者が対象チームの管理画面を開く
4. アプリ名、概要、使い方、APIエンドポイント、APIキー、リクエスト形式などを登録する
5. JSONのリクエスト定義を基に、利用者向けの入力画面が自動生成される
6. 対象チームの利用者が源内WebからAIアプリを実行する

入力画面では、テキスト、数値、テキストエリア、ファイル、セレクトボックス、チェックボック、ラジオボタンなどを定義できる。実行方式は同期・非同期に対応し、テキストとファイルを出力できる。

### 5.3 自治体での価値

カスタムAIアプリはチーム単位で管理・公開できる。例えば、次のような課室固有のAIアプリを、共通の源内Webから提供できる。

- 財務課向けの予算照会
- 人事課向けの規程検索
- 広報課向けの文案作成
- 福祉部門向けの制度案内支援

> 源内は、外部で開発した業務固有のAIアプリを、共通の入口から組織単位で展開するためのポータルとして機能する。

なお、源内の登録機能がAIアプリ自体を開発するわけではない。AIアプリの開発・デプロイ、API仕様への適合、APIキー管理、接続元IPアドレスの制限などは別途必要である。

### 5.4 OSSで公開されているカスタムAPIの実装例

デジタル庁は、源内Webとは別の`genai-ai-api`リポジトリで、中央省庁に実際に展開されている行政実務用AIアプリの一部を公開している。これらは、源内WebのカスタムAIアプリ連携を実装する際の参照例となる。

#### Amazon Web Services：行政実務用RAG

AWS向けには、Knowledge Bases for Amazon Bedrockを使ったクエリ拡張RAGの開発テンプレートが公開されている。

```text
利用者の質問
  → 検索クエリを複数に拡張
  → Bedrock Knowledge Baseを検索
  → 取得結果の関連性を評価
  → 根拠を基に回答を生成
```

主にAPI Gateway、Lambda、Bedrock Converse API、Bedrock Knowledge Base、OpenSearch Serverless、S3で構成される。APIキーとWAFのIPアドレス制限に対応し、データやログはKMSのカスタマー管理キーで暗号化される。設定ファイルを変更することで、異なるプロンプトや仕様を持つ複数のRAGアプリを同じコードベースからデプロイできる。

#### Google Cloud：法制度に関するAIアプリ

Google Cloud向けには、最新の法律条文データを参照して回答する、法制度に関するAIアプリの再現可能な実装が公開されている。BigQueryに法令データを格納し、BigQuery MLとVertex AIを使って検索・生成する。回答には条文番号やe-Gov法令検索への参照を含める。

この実装は、「法令」×「デジタル」ハッカソンの最優秀賞に選ばれたLawsyを基に、ガバメントクラウド内で完結するよう再設計されている。

#### Microsoft Azure：LLMセルフデプロイ用テンプレート

Microsoft Azure向けには、Hugging FaceのvLLM対応モデルやAzure OpenAIのモデルをAzure上にホスティングし、APIとして提供する開発テンプレートが公開されている。vLLMの実装例としてPLaMo翻訳モデルを使い、Azure OpenAIのChat Completions、Responses API、Code Interpreterを提供する構成も含む。

Azure API Managementで単一の入口、APIキー認証、接続元IP制限、ルーティングを提供し、バックエンドへの通信をプライベート化できる。

### 5.5 公開サンプルが示すこと

これらの公開例は、源内のカスタムAIアプリが特定のクラウドやモデルに固定されないことを示している。源内Webとの間のAPIプロトコルに準拠すれば、AIアプリは源内Webから独立したAWS、Google Cloud、Microsoft Azureの環境に構築できる。

提案時には、これらを完成品の業務アプリとしてそのまま採用するのではなく、次の観点で参照する。

- 源内WebとカスタムAIアプリの接続方法
- APIのリクエスト・レスポンス実装
- APIキーと接続元IPによるアクセス制御
- クラウドごとのIaCとデプロイ方法
- 独自の業務データ、プロンプト、モデルへの置き換え方

## 6. デジタル庁の方針とOSSの位置づけ

### 6.1 源内の主体

源内は、デジタル庁が中心となって開発・運用する生成AI利活用基盤である。行政職員が業務特化の生成AIアプリを迅速、安全かつ簡単に利用できる環境の提供を目的としている。

### 6.2 OSS公開は源内の一部

「源内」のすべてがOSSとして公開されているわけではない。デジタル庁の公式説明では、源内の「一部」をOSSとして公開したとされている。現在公開されているのは、「源内Web（AIインターフェース）」のソースコード等である。

したがって、次の2つは区別して説明する。

- デジタル庁が開発・運用する源内全体
- 自治体や政府機関が参照・再利用できる公開OSSとしての源内Web

### 6.3 公開の狙い

源内の一部をOSSとして公開することには、次の狙いがある。

- 地方公共団体や政府機関における類似AI基盤の重複開発を防ぐ
- 社会全体の開発コストを削減する
- 各機関が自らの要件に合わせてAI基盤を改変・運用できるようにする
- 調達仕様書における実装の参照先とする
- 民間企業による自治体向けAIサービスの開発・提供を促す

この方針を踏まえると、源内Webをそのまま導入するだけでなく、自治体ごとの要件に合わせた設計・実装・運用支援が提案価値となる。

## 7. 結論

本番運用、特に官公庁・自治体向けに提供する場合は、源内を推奨する。

GenUと源内は、AWS上で生成AI機能を提供するWebアプリケーションという共通の骨格を持つ。しかし、主な設計目的は異なる。

- GenUは、AWSの多様な生成AIサービスとユースケースを素早く試すPoCのための基盤
- 源内は、組織・チーム単位の統制、AIアプリ管理、運用・監視を含む、行政機関での本番運用を見据えた基盤

> PoCでAWSの生成AI機能を広く試すならGenU、官公庁・自治体で継続的に本番運用するなら源内を軸にする。

## 8. 補足・留意事項

### 8.1 閉域化にはカスタマイズが必要

公開版の源内Webの標準構成は、CloudFrontのURLまたはカスタムドメインからのアクセスを想定しており、閉域環境での利用を前提とした標準構成ではない。

自治体の閉域環境で利用する場合は、次の要素を個別に設計する。

- 利用者から源内Webまでの接続経路
- AWSサービスへのプライベート接続
- 庁内の認証基盤との連携
- 外部AIアプリへの通信経路
- ログ、監視、デプロイ、保守の運用経路

閉域環境の定義と許可される外部通信は自治体ごとに異なる。対象ネットワークの要件を確認した上で実現性を評価する必要がある。この閉域化の設計・実装・運用支援は、導入ベンダーの付加価値になり得る。

### 8.2 デジタル庁の動向を継続的に確認する

源内はデジタル庁が開発・運用する基盤であり、公開OSSはその一部である。また、AIアプリAPI仕様は試行錯誤中で、将来大きく変更される可能性があると明記されている。

提案・設計時には、次の情報を最新化する。

- 公開OSSの対象範囲
- 源内Webの機能とアーキテクチャ
- AIアプリAPI仕様
- デジタル庁による保守・更改方針
- 地方公共団体と民間企業による導入事例

現時点の公開情報を固定的な製品仕様と捉えず、デジタル庁の方針と公開リポジトリの変更を継続的に確認する必要がある。
